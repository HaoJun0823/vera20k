# Auto play v2：以能力画像驱动的策略层

**状态：计划书。** 实施后它取代 `sim::strategy::retail` 的内部结构；
`docs/autoplay.md` 仍作为操作层的记录，`docs/ai-layers.md` 仍作为分层契约，
直到第 4 阶段把本文并进去。

## 1. 为什么要重写

现在的 L3 是约 1.1 万行、按"机制"排列的 pass。分配是排列顺序的副作用，
所以策略层没有一处能回答"这个单位这一帧在干什么"。由此产生四个已观察到的失败：

- `Outbox` 的 rank 映射，是因为"最后说话的 pass 拥有对象"；它自己的注释记录了
  修好一个 pass 的优先级就打开了下一个 pass 的洞。
- 每个 pass 都以"留给别的 pass"收尾（无武器的工程师等本方的枪去打墙；墙的圈
  等一个一直被别人占着的格子）。等待期间没有任何一层拥有这个单位。
- census 默认是全知的；雾形不同的地图会改变策略能看到什么，结果无法迁移。
- 唯一的验收是一张图一个种子。泛化性从未被测量，所以"测试过了、换张图就烂"
  是预期结果，不是意外。

另外：类型名和调参常数写死在策略里，mod 新增的单位对它是不可见的。

## 2. 目标与非目标

目标

1. **推导，不声明。** 关于单位的一切事实都在加载规则时算出。代码里没有类型名，
   没有按单位写的表。mod 新增一个单位，只要规则描述得出来，策略就能用它。
2. **一个单位一个主人。** 每个可控单位每个任期恰好一个任务，每个任务都会结束。
   `Unowned == 0` 是一条不变量测试。
3. **可归因。** 每个决定都有结果和原因，只记录一处，所以回归能指名某个机制，
   而不是挪动一个 tick 数字。
4. **低耦合。** 策略是独立 crate，架在只读投影和命令入口之上。core 不带它也能
   编译。外部控制器（Lua、Python、模型）可以替换它而不碰引擎。
5. **在四张图上测量。** 矩阵说完成，才算完成。

非目标

- 与 `gamemd` 自己的 AI 完全对齐：原生已有答案的地方（队伍创建、队伍脚本、
  `AI_Choose_Unit`、放置）我们调用它，不重新实现。
- 新的回放格式、渲染工作、进程外传输。
- 现在就上脚本化。第 7 节让以后变便宜，它不是 v2 的一部分。

## 3. 模型一：单位画像（动态特性）

每个对象类型一份 `UnitProfile`，按规则集计算一次，用仿真自己的读取器
（`src/rules/ini_value.rs`），缓存、不可变。

| 组 | 来源键 | 推导出的量 | 消费者 |
|---|---|---|---|
| 角色 | `Harvester=`、`Weeder=`、`Engineer=`、`Agent=`、`C4=`、`Gunner=`、`Passengers=`、`Deployer=`/`UndeploysInto=` | `Role` 集合，不是单一枚举 | 任务资格 |
| 武器 | `Primary`/`Secondary`、`Damage`、`ROF`、`Burst`、`Range`、`Projectile`、`Speed`、`Warhead`、`CellSpread`、`TargetFlags` | 每件武器：**对每种装甲的每秒伤害**、以格计的射程、溅射格数、能否打空/地/建筑 | 目标选择、破墙、交战 |
| 生存 | `Strength`、`Armor`、`Sight`、`Speed`、`Locomotor`、`MovementZone` | 有效血量、视野、机动等级 | 分配评分、撤退 |
| 经济 | `Cost`、`Storage`、`Refinery=`、`ResourceGatherer=`、`UnloadingClass=` | 一台单位每分钟能搬多少钱、回本时间 | 经济计划 |
| 通用 | `Power=`、`Radar=`、`SuperWeapon=`、`BuildCat=`、`Prerequisite=` | 这个建筑解锁了什么 | 计划闸门 |

推导规则：

- 对某目标的有效性来自 `warhead Verses × armor`，不是代码里的表。
  "这个单位能不能伤到那个"是一个计算出的谓词。
- 射程用仿真自己的换算（`advance::weapon_range_cells` 背后那一条），
  不另造第二个换算。
- 画像表达不了的能力，是一个显式的 `Capability` 变体加一条残差说明，
  不是静默的默认值。
- `tools/autoplay_profiles` 把所有画像导出为 JSON。审阅这个文件，是把
  "策略认为灰熊打得过犀牛"从猜测变成可检查的断言的方式。

## 4. 模型二：任务与分配

任务是单位唯一能拿到的东西。pass 不再存在，只剩任务的生产者。

| 任务 | 需要 | 目标 | 结束条件 |
|---|---|---|---|
| Harvest / ReturnOre | `Role::Harvester` | 矿田、矿厂 | 空、满，或矿田消失 |
| Repair | `CanRepair` | 受损建筑 | 修满，或资金不足 |
| Capture / Garrison | `Role::Engineer` / `Occupier` | 建筑 | 占领、进入，或不可能 |
| Breach | `CanHurt` 该障碍 | 路线上第一个封闭格 | 通路打开，或放弃 |
| Assault | `CanHurt` 目标 | 敌方对象 | 摧毁、无效，或被召回 |
| Defend | 任意战斗单位 | 己方建筑附近一格 | 威胁解除或缓解 |
| Scout / Transport / Retreat | 按角色 | 区域、单位、家 | 到达、完成，或不安全 |

- 分配在提案处进行，每任期一次（默认 15 帧），不是每帧；反应型任务
  （闪避、撤退）可以在任期内抢占。
- 排序是字典序的**整数**键：种类优先级、能力匹配、距离平方、稳定 id。
  决定里不使用 `f32`（`strategy/brain.rs` 已有这条规则）。
- 一个单位一个任务。同一单位被二次提案记为 `Displaced`，不静默丢弃。
- 每个任务报告 `Done` / `Unreachable` / `Ineffective` / `Stalled`。
  每种原因只有一条阶梯，每条阶梯都会终止：改道、换目标、交给别的角色、
  或放弃并冷却。"等别的 pass"不是允许的终点。
- 没有任务的单位拿到默认任务：防守最近的己方建筑。这是 `Unowned == 0`
  在构造上成立的原因。

## 5. 模型三：军队

军队由原生队伍块执行，不由 pass 驱动。

- 策略只决定**按角色槽位**的编成（四个战斗、一个防空、一个攻坚……），
  用画像校验，然后向本方申请最接近的 `TeamType`。
- 原生队伍脚本负责移动和开火；策略只负责组建、改目标和解散。
- 前置条件：必须先有一条测试证明被策略驱动的房子，队伍脚本能跑到 `Done`。
  在此之前本阶段不启动。

## 6. 模型四：经济

一个显式状态机，输入是实测收入和画像回本，不是一串钱包阈值：

```
收入 < 目标  -> 继续加矿车/矿厂，直到边际回本超过任期
收入 >= 目标 -> 把盈余花在编成目标上
停滞         -> 带原因（没有矿车、没有可达的矿、钱包满）
```

停滞是一个带原因的一等状态，所以"AI 停产了"是一条读数，不是一个症状。

## 7. 端口（core 保留什么）

core 只保留五样东西，其余全在依赖它们的独立 crate 里：

1. `Command` 与 `queue_commands` —— 唯一写入路径，与玩家点击共用。
2. `Observation` —— 只读的拉取式投影，增加 `profile(type_id)`，
   让策略层不必自己再读规则。
3. `Brain` / `Outbox` —— 决策端口。
4. 一个安装钩子。
5. 一个 feature gate（`autoplay`），使不带策略层的构建存在。

拉取式 API 优先：策略要什么就问什么。每帧张量（`control::external`）
保留为架在它之上的一种适配器，不作为主要形态——两万单位推不起全量快照。

## 8. 测量契约

- **矩阵**：Barrel.mmx（日常 1v1）、Death.mmx（`--opponents 1..7`）、
  xeb1.map（中立围墙 / 破墙）、xtsunami.map（四岛 / 运输 / 海战）。
  8 个种子、12k tick、并行。
- **每次运行的向量**：各计划节点的首次 tick、收入曲线、军队价值、损失、
  `Unowned`、`Stuck`（持有移动任务但格子不变）、`Idle`、打开的墙段、
  登陆非起始岛的单位数、撑住的最高 `N`。
- **决策追踪**：每任期、每单位：任务种类、目标、结果、原因。同一 seed 上两个
  构建做差分，定位到第一条分歧的任期和改变它的任务。
- **能力登记表**：每个能力（IFV 乘员换武器、运输、驻扎、改目标、防御塔指定
  目标）都要有一条命令路径和每局使用计数。计数为 0 就是"没接上"，
  无论代码里写了什么。
- **验收**：矩阵没有一格变差；点名的计数改善；撑住的最高 `N` 不许下降。

## 9. 阶段

| 阶段 | 工作 | 退出条件 |
|---|---|---|
| 0 | 矩阵、追踪、能力登记表 | 四张图的基线表 |
| 1 | 拆出策略 crate、feature gate | core 不带它可编译；结果完全一致 |
| 2 | `UnitProfile` + `profiles.json` | 每个可造类型都有画像；用零售 INI 抽查通过 |
| 3 | 任务 + 分配，先只接管采矿与工程 | `Unowned = 0`、发呆下降、无回归 |
| 4 | 军队走队伍；逐个角色删除战斗 pass | 1vN 曲线保持或改善 |
| 5 | 经济状态机 | 不停滞、收入曲线单调 |
| 6 | 能力接线，每个带计数 | 矩阵里每个计数 > 0 |
| 7 | 再决定外部控制 | 只有具体控制器需要时才做 |

阶段 0–2 不改变行为。之后每个阶段在同一次改动里删除自己的旧代码，不留双路。

## 10. 会被删除的东西

`retail::think` 里的 pass 顺序与 `Outbox` 的 rank 仲裁；`tracked.rs`
作为"说过什么"的记录（由任务结果取代）；`plan.rs` 里的钱包阈值；
类型名匹配；全知 census 默认值；那一串"留给别的 pass"的分支。

## 11. 风险

- 画像无法表达所有单位（分段武器、敞篷载员射击）。每个缺口是一个具名的
  `Capability` 变体加残差，不是静默兜底。
- 任务抖动：任务带任期和冷却；同一个单位因同一原因被放弃两次后，本局不再
  为它提这个任务。
- 被驱动房子的队伍脚本可能跑不到 `Done`；这一点在第 0 阶段就测，
  而不是等第 4 阶段依赖它时才发现。
- 成本：两万单位下的分配必须留在每帧路径之外。
