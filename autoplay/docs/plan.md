## 排序的三条原则

1. **先做能立刻验收的。** 判据必须能在一次 `tools/autoplay_check.py` 运行里读出来，
   不需要打完整一局文明。占领、运输、驻扎都符合；"打得更好"不符合。
2. **先做不会互相打架的。** 之前三次失败（精炼厂预留、购买下限、科技预留）都是
   同一个病：**一个模块省钱，另一个模块就饿死**。同一轮里只动一个模块的预算。
3. **先做不依赖胜负的。** 强度先不追，功能先补齐——你已经定了这个方向。

## 判据的可观测性（这一节决定计划能不能执行）

计划的每一条判据必须是**现在就能读到的**，否则计划只是愿望。当前的读数：

| 读数 | 来源 | 能判什么 |
|---|---|---|
| `capabilities` 表 | `jobs used` / `never asked for` | 某个 **job 种类**是否被提议过 |
| `own` / `enemy` / `army` / `lost` | census | 房子规模、血量、交换 |
| `stuck` / `unowned` | policy 统计行 | 卡死、无主单位 |
| `military:` 行 | 每 1800 帧 | `seen` / `near` / `engage` / `march` / `order` |
| `economy:` 行 | 每 1200 帧 | 钱、精炼厂、防御、科技建筑、候选是否可用 |

**能被 `capabilities` 表直接验收的**：A1（工程师存活要靠 `Capture` 出现次数）、
B2/B3（`Garrison`）、C1/C3（`Transport`）、C2（`Breach`）、D2（`Retreat`）、
D4（渗透要先加 job 种类）、D5（超武）。

**不能直接验收、需要先加读数的**：
- A2 躲避——`Scatter` 是命令不是 job，表里没有。要么加一行躲避计数，要么把躲避
  做成 `Retreat` 下的一个 job。
- A3 无效交战——需要一个"对无效目标的攻击命令数"计数，现在没有。这条可以先靠
  代码里的 `engage_error` 断言（单元测试），矩阵上看 `lost` 变化。
- D1 风筝、D3 弹药分配——都需要新的计数。

所以每一批的第一步，通常是**先把判据变成可读的**，再改行为。这是这一版验收工具
（`accepts_brain_flag`、`capabilities`）存在的理由。

跑这一条命令就够：

    python -m tools.autoplay_check --brain v2 --seeds 0x5EED --maps Death.mmx ^
        --ticks 12000 --opponents 1 --difficulty easy ^
        --history target/autoplay-results/<批次名>.jsonl

读两样：

1. **`capabilities` 表**——你关心的那条功能是不是从 `never asked for` 变成非零；
2. **`own` / `lost` / `stuck`**——确认这一批没把对局搞崩。

不需要 1v7，不需要赢。**功能验收与胜负无关**，这是这一轮定的规矩。
