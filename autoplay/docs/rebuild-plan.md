## 二、Sorian 的架构，和我们差在哪

### 它只有一个核心概念：Platoon（编队）+ 长期协程

`schook/lua/platoon.lua` 第 46–1700 行，每种任务是一个**长期运行的函数**：

```
NukeAISAI, BaseManagersDistressAI, PauseAI, UnitUpgradeAI,
AirHuntAI, FighterHuntAI, AttackForceAI, ReclaimStructuresAI,
RepairAI, SorianManagerEngineerAssistAI ...
```

`OnCreate` 里的关键一行（第 8 行附近）：

```lua
if self[plan] then
    self.AIThread = self:ForkThread(self[plan])   -- 每支队伍一个协程
end
```

**每支队伍跑在自己的线程里**，不是每帧全局重排。

### `AttackForceAI` 的真实节奏

`platoon.lua:1274` 起，主攻循环：

```
GatherUnits()          -- 先集结
while PlatoonExists:   -- 只要队伍活着
   ...
   WaitSeconds(30)     -- 每 30 秒重估一次
```

**每 30 秒重估一次。** 对比我们的 `TERM_FRAMES = 15`（约 0.2 秒），**差 150 倍**。

这就是“改动互相抵消”的数学来源：我们每秒重排 5 次，任何单点改动都会被下一次重排抹掉。

### `GatherUnits`：我们完全缺失的一层

`platoon.lua:1234` `GatherUnitsSorian`：

1. 检查全队是否都在队长 60 格以内（`3600` 是平方距离）
2. 有掉队 → 找集结点：`Rally Point` → 退而 `Defensive Point` → 再退当前位置
3. 命令全队移动过去
4. **每 1 秒检查一次，最多 20 次**（20 秒超时）
5. 集结完成才继续；队伍死了就退出

**我们的策略没有这个概念。** 每个单位独立找目标、独立行军，
所以永远是“一拥而上、各自为战”，这也是 68% 军费买了打不动装甲单位的根源。

### 建造按兵种分文件

`lua/AI/AIBuilders/` 下 14 个文件，按用途分开：

```
SorianLandAttackBuilders.lua   61 KB   陆战编队
SorianAirAttackBuilders.lua    91 KB   空袭编队
SorianSeaAttackBuilders.lua    23 KB   海战编队
SorianArtilleryBuilders.lua    22 KB   炮兵编队
SorianDefenseBuilders.lua     111 KB   防御
SorianEconomicBuilders.lua    127 KB   经济
SorianExpansionBuilders.lua    38 KB   扩张（分基地）
```

**兵种组成不是“按比例买”，而是“先决定要几支什么样的队伍，再凑齐”。**

## 三、我们现在的真实状态（实测数据）

| 项 | v2 |
|---|---|
| 决策周期 | **15 帧**（约 0.2 秒） |
| 编队概念 | **无**（搜 `team`/`squad` 零命中） |

| Barrel easy | 6/6 胜 |

**结论：v2 缺的不是“更好的战术”，是中间层。**

## 四、重构方案

### 目标（DONE WHEN）

- v2 有明确的编队层：单位归属某支队伍，队伍有任务
- 决策频率降到秒级而不是帧级
- Barrel easy 保持 6/6（不得退步）
- Death easy 从 0/6 提升到 **≥2/6**
- 交换比不劣化

### 四个阶段，每阶段独立可验收

#### 阶段 1：编队层（最关键，先做）

借 `squads.rs` 的设计（同仓库已实现，可直接读）：

- 队伍 = **角色 + 成员**，不是阵型也不是状态机
- 角色：`Hold`（守家）、`Scout`（侦察）、`Attack`（主攻）
- 成员**每 300 帧重建**（不是招募制，避免记账错误）
- **目标锁定 1800 帧**（2 分钟），这是防“打一半换目标”的关键

验收：单位不再每秒重排；日志里能读出每支队伍的任务。

#### 阶段 2：集结（GatherUnits 移植）

照 `GatherUnitsSorian` 实现：

- 全队在队长 60 格内才算集结完成
- 掉队 → 集结点（Rally → Defensive → 当前位置）
- 每 1 秒检查，最多 20 秒超时
- **集结完成才允许进攻**

验收：进攻前日志显示队伍已集结；散兵进攻次数显著下降。

#### 阶段 3：兵种按队伍组织

把“按比例买兵”改成“先定队伍编制，再补齐”：

- 主攻队：`灰熊 ×12 + IFV ×4 + 步兵 ×6`（能打装甲的占多数）
- 防御队：`步兵 + 狗 + 防空`
- 侦察队：`1–2 个最便宜的步兵`

这一条直接针对今天的实测差异：Barrel 胜局灰熊占 32%，Death 只有 21%。

验收：Death 上灰熊占比 ≥30%。

#### 阶段 4：威胁与绕路

借 `threats.rs`（同仓库，16 格空间索引）和 Sorian 的威胁表：

- 建立“这个格子被什么火力覆盖”的索引
- 行军路径避开防御塔射程

这条对应许愿书第 109 行“不会绕路，正面都是防御塔还打正面”。

验收：进攻路径避开已知防御塔；同类进攻损失下降。

## 五、验证协议（这一条是流程改进，不是技术）

今天的九次失败里，有几次在 30 秒内就能看出崩了，我却跑完整个矩阵。

新协议：

| 阶段 | 样本 | 时间 | 判据 |
|---|---|---|---|
| 冒烟 | 1 格 × 8000 ticks | 30 秒 | 不崩、无异常 |
| 方向 | 3 格 × 24000 ticks | 3 分钟 | 胜局数、交换比 |
| 确认 | 6 格 × 24000 ticks | 8 分钟 | 通过才进下一步 |

**冒烟或方向不过，直接回退，不进下一步。**

指标也要换：不用 `own`（它被十几个因素混淆），用**交换比**（杀伤/损失）
和**每单位杀伤**。今天 `lost 0:7` → `5:41` 时 `own` 只动了 9，交换比动了 30 倍。

## 六、风险与取舍

| 风险 | 说明 | 应对 |
|---|---|---|
| **编队可能比单位池更差** | 1v7 那次的教训：把单位从战线抽走就崩 | 先在 1v1 验证；1v7 单独测 |
| **改动面大** | 编队 + 集结 + 编制 + 威胁，四个阶段 | 每阶段独立提交、独立验收，不合并 |
| **Barrel 6/6 是硬约束** | 任何阶段掉出 6/6 立即回退 | 每阶段结束都跑 Barrel 6 格 |
| **`RetailBrain` 可能已经够用** | 它 Death 2/6、会围墙、会分基地 | **先问：要废掉 retail 的话，v2 必须先达到它的水平** |

## 七、一个必须先确认的问题

你说 `retail` 打算废弃掉。但它当前**比 v2 强得多**：

| | v2 | retail |
|---|---|---|
| Death easy | 0/6 | **2/6** |
| own（Death） | 81–101 | **116–147** |
| 围墙 | 0 | 26–55 段 |
| 分基地 | 0 | **1–2 个** |

废弃它之前，v2 至少要达到这个水平，否则等于用一个更弱的 AI 换掉更强的。

**我的建议：把 `retail` 当“陪练”保留，v2 每阶段跟它对比。** 这比任何自设指标都可靠。

---

## 八、不做什么

- 不再调参（今天证明了两次：2→3 有效，3→4 就退步）
- 不再改行军路径（`can_reach` 那种“语义正确”的改动也会重排对局）
- 不同时改两处（今天多次无法归因）
